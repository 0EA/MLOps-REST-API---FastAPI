# MLOps REST API — FastAPI (Iris classifier demo)

A small, complete example of **model serving** for a university MLOps presentation.
It trains a scikit-learn classifier on the bundled Iris dataset and serves it
behind a REST API built with FastAPI.

## The problem this example solves

Training a model only produces an artifact on disk; it does not make the
model usable by anything else. **Model serving** is the step that turns a
trained artifact into a network service other systems (a web app, a batch
job, another microservice) can call to get predictions. This repo
demonstrates that step end to end with the smallest model that still makes
the pattern obvious: load Iris → train a pipeline → persist it → load it once
in a long-running process → answer HTTP requests with real inference.

## Where this fits in the ML lifecycle

```
 data            training              packaging                serving                 consumption
 (Iris)  ─────▶  (scripts/train.py) ─▶ (model.joblib +     ─▶   (FastAPI app,     ─▶    (Swagger UI /
                 fit Pipeline,          metadata.json,           loaded once at          Python client /
                 measure accuracy)      versioned on disk)       startup via lifespan)   any HTTP caller)
```

Training and serving are deliberately **separate processes**: `scripts/train.py`
is run explicitly, once, to produce artifacts; `app/main.py` only ever reads
those artifacts. The API never trains or retrains a model while handling a
request.

## Request → validation → inference → response

```
        HTTP POST /predict                                                  HTTP response
        {sepal_length_cm, ...}                                              {predicted_species,
               │                                                             probabilities, ...}
               ▼                                                                   ▲
      ┌─────────────────┐     ┌────────────────────┐     ┌──────────────────┐     │
      │ Pydantic schema │ --> │ feature vector in   │ --> │ pipeline.predict /│ ----┘
      │ (IrisMeasurement│     │ FEATURE_ORDER       │     │ predict_proba     │
      │ Request):       │     │ [sepal_length_cm,   │     │ (StandardScaler + │
      │ 4 required      │     │  sepal_width_cm,    │     │  LogisticRegress.)│
      │ finite, >0      │     │  petal_length_cm,   │     │ loaded once at    │
      │ floats; extra   │     │  petal_width_cm]    │     │ startup           │
      │ fields rejected │     └────────────────────┘     └──────────────────┘
      └─────────────────┘
               │
               ▼ (validation failure)
        HTTP 422 Unprocessable Entity
```

## Setup (Windows PowerShell)

Requires Python 3.11+ (tested with 3.13.3 — no 3.11/3.12 interpreter was
available on this machine; any of 3.11–3.13 should work identically).

```powershell
py -3.13 -m venv .venv
.venv\Scripts\python.exe -m pip install --upgrade pip
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

All commands below call `.venv\Scripts\python.exe` directly, so activating
the virtual environment first is optional.

## Train the model

Explicit, separate step. Writes `artifacts/model.joblib` and
`artifacts/metadata.json`.

```powershell
.venv\Scripts\python.exe scripts\train.py
```

Expected output (your held-out accuracy is computed fresh each run on a
fixed 80/20 stratified split, `random_state=42`):

```
Trained iris-logreg-1.0.0
Held-out accuracy: 0.9333
Artifacts written to: ...\artifacts
```

**Actual measured metric in this repository: held-out accuracy = 0.9333
(28/30 correct) on a 30-sample stratified test split.**

`artifacts/model.joblib` and `artifacts/metadata.json` are git-ignored (see
`.gitignore`) — a fresh clone only contains `artifacts/.gitkeep`. This is
expected, not a missing file: run the training command above once and both
files are regenerated locally.

## Run the server

```powershell
.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

If `artifacts/model.joblib` or `artifacts/metadata.json` is missing, startup
fails immediately with an error naming the exact training command to run —
the server will not silently train a model for you.

Open Swagger UI: http://127.0.0.1:8000/docs
Raw OpenAPI schema: http://127.0.0.1:8000/openapi.json

## Browser dashboard

**Open http://127.0.0.1:8000/ in Chrome** — this is the main interface for
presenting the system live, so the audience sees inputs, predictions, raw
HTTP traffic, and validation errors without anyone reading terminal logs.

It is served by the same FastAPI process, as plain HTML/CSS/JS under
`GET /` and `GET /static/*` (`app/static/`) — no separate frontend server,
no Node build step, no framework. All requests the dashboard makes
(`/health`, `/model-info`, `/predict`) are same-origin `fetch()` calls using
relative URLs, exactly like `scripts/demo_client.py` or Swagger UI — the
dashboard has no special access to the model; it is just another HTTP
client.

What each section demonstrates:

| Section | What it shows | Where the data comes from |
|---|---|---|
| **Service & model status** | API reachability, whether the model is loaded, model version, held-out test accuracy, dataset/feature info | Live `GET /health` and `GET /model-info` responses, fetched on load and on **Refresh status** |
| **Flower measurements** | The four required inputs, a sepal-vs-petal schematic, sample presets, and an explicit "Send invalid request" action | Local form state only — nothing is sent until you press a button |
| **Prediction result** | Predicted species and one probability bar per class | The exact JSON body of the most recent `POST /predict` response |
| **HTTP inspector** | Method, path, timestamp, outgoing JSON, actual status code, response JSON/text, round-trip time, and a conceptual request-flow diagram | The same request/response pair just sent or selected from history |
| **Requests from this page** | Up to the last 20 prediction attempts made from this browser tab | Kept in page memory (a JS array); resets on reload, never written to disk or a database |

Three numbers that look similar but are **not** the same thing, all visible
on this one page:
- **Held-out test accuracy** (status panel) — one fixed number, measured
  once by `scripts/train.py` on the 30-sample test split, read from
  `GET /model-info`.
- **Per-request probabilities** (result panel / inspector) — `predict_proba`
  output for the one measurement you just submitted; changes with every
  request.
- **Round-trip time** (inspector / history) — wall-clock milliseconds the
  *browser* measured between sending the request and finishing reading the
  response. It is network + server time combined, not a model-inference
  benchmark, and it is explicitly not labeled as one.

## Run the tests

```powershell
.venv\Scripts\python.exe -m pytest tests/ -v
```

Tests train their own model into a pytest `tmp_path` directory (via the
`MODEL_ARTIFACTS_DIR` environment variable) — they never read or overwrite
the real `artifacts/` used by the live demo. `tests/test_dashboard.py` adds
focused checks that `GET /` serves the dashboard HTML, `/static/styles.css`
and `/static/app.js` are reachable, and `/docs`/`/openapi.json` are
unaffected — no cosmetic snapshot assertions.

## Run the demo client

With the server already running in another terminal:

```powershell
.venv\Scripts\python.exe scripts\demo_client.py
```

It calls `/health` and `/model-info`, sends one valid prediction, sends one
intentionally invalid request and checks it gets HTTP 422, and exits with a
nonzero status if anything doesn't match expectations.

## Endpoints

### `GET /health`
Liveness probe.

```json
{ "status": "ok", "model_loaded": true }
```

### `GET /model-info`
Metadata about the currently loaded model (version, dataset, feature order
and units, target classes, held-out accuracy, random seed, package
versions).

### `POST /predict`

Request body — all four fields required, units are **centimeters**, values
must be finite and strictly positive, unknown fields are rejected:

```json
{
  "sepal_length_cm": 5.1,
  "sepal_width_cm": 3.5,
  "petal_length_cm": 1.4,
  "petal_width_cm": 0.2
}
```

Response — probabilities cover all three species and are built from the
model's actual internal class order (not an assumed order):

```json
{
  "predicted_species": "setosa",
  "probabilities": {
    "setosa": 0.9808,
    "versicolor": 0.0192,
    "virginica": 0.0000003
  },
  "model_version": "iris-logreg-1.0.0"
}
```

### Triggering HTTP 422 on purpose (PowerShell)

`Invoke-RestMethod` throws on non-2xx status, so wrap it to inspect the
error body. This sends a negative measurement and an unknown field:

```powershell
$body = @{
  sepal_length_cm  = -1.0
  sepal_width_cm   = 3.5
  petal_length_cm  = 1.4
  petal_width_cm   = 0.2
  unexpected_field = "nope"
} | ConvertTo-Json

try {
  Invoke-RestMethod -Uri http://127.0.0.1:8000/predict -Method Post `
    -ContentType "application/json" -Body $body
} catch {
  $_.Exception.Response.StatusCode.value__   # 422
  $_.ErrorDetails.Message                    # validation error detail
}
```

A valid call, for comparison:

```powershell
$body = Get-Content examples\valid_request.json -Raw
Invoke-RestMethod -Uri http://127.0.0.1:8000/predict -Method Post `
  -ContentType "application/json" -Body $body
```

Note: PowerShell's `curl` is an alias for `Invoke-WebRequest`, not Unix curl —
its flags (`-X`, `-d`, `-H`) are not the same. The examples above use
`Invoke-RestMethod` directly to avoid that confusion.

## Why `/predict` is a plain `def`, not `async def`

`pipeline.predict`/`predict_proba` are blocking, CPU-bound scikit-learn
calls. Writing `async def predict(...)` would **not** make that call
non-blocking — there is no `await` inside it, so it would simply run on
FastAPI's single event loop and block every other concurrent request for its
duration. FastAPI's documented behavior for a plain `def` endpoint is the
opposite: it runs the function in a worker thread from a thread pool,
keeping the event loop free. For a blocking, synchronous call like this,
plain `def` is the correct and faster choice under concurrent load. See
[FastAPI's own docs on this exact tradeoff](https://fastapi.tiangolo.com/async/#path-operation-functions).

## Concepts, briefly

- **REST / HTTP** — an architectural style where resources (here, "a
  prediction") are addressed by URLs and manipulated with standard HTTP
  methods (`GET` to read, `POST` to create/compute) and status codes (`200`
  success, `422` invalid input). [MDN: HTTP overview](https://developer.mozilla.org/en-US/docs/Web/HTTP/Overview).
- **FastAPI** — a Python web framework that generates request validation,
  serialization, and interactive docs directly from type-annotated function
  signatures. [FastAPI docs](https://fastapi.tiangolo.com/).
- **Pydantic** — the data-validation library FastAPI uses under the hood;
  `BaseModel` subclasses declare the exact shape and constraints of valid
  data. [Pydantic docs](https://docs.pydantic.dev/latest/).
- **Uvicorn** — the ASGI server that actually accepts TCP connections and
  runs the FastAPI application. [Uvicorn docs](https://www.uvicorn.org/).
- **OpenAPI** — the machine-readable schema (`/openapi.json`) that FastAPI
  generates automatically from the same type annotations; Swagger UI
  (`/docs`) renders it as an interactive page. [OpenAPI spec](https://swagger.io/specification/).
- **Lifespan** — a FastAPI/ASGI hook that runs once before the app starts
  accepting requests and once after it stops accepting them; used here to
  load the model exactly once per process instead of per request.
  [FastAPI docs: Lifespan events](https://fastapi.tiangolo.com/advanced/events/).

## Limitations (read before presenting as more than a demo)

- This is an **educational classifier** on a toy dataset. Iris is linearly
  separable for two of its three classes and has only 150 total samples;
  93.3% held-out accuracy here says nothing about how any model would
  perform on real, messier data.
- No authentication, rate limiting, logging/observability, containerization,
  or deployment pipeline is included — out of scope for this demo on
  purpose, per the assignment.
- No model monitoring, drift detection, or retraining pipeline — this
  repository only covers the "serve a trained model" slice of MLOps.
- Single-process, single-model, in-memory serving. It does not demonstrate
  scaling, versioned rollouts, or multi-model routing.

## Working offline

After `pip install -r requirements.txt` has completed once (which needs
internet), the API itself, the **browser dashboard at `/`**, and
`scripts/demo_client.py` make **no external network calls** — training uses
scikit-learn's bundled Iris dataset, inference is pure local computation,
and the dashboard's CSS/JS are served locally from `app/static/` with no
CDN, external font, or remote image references.

The one exception: **Swagger UI (`/docs`) loads its JS/CSS from a public CDN
by default**, so opening `/docs` without internet may render a blank page
even though the API underneath is working fine. `/openapi.json` and every
actual endpoint (`/health`, `/model-info`, `/predict`) still work offline.
If `/docs` won't load during the live demo, use the dashboard at `/` or
`scripts/demo_client.py` instead — both only talk to `127.0.0.1`.
